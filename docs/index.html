Logs that prove they weren't changed.

An insider with admin access can edit a balance and then edit the logs to hide it. Chain of Custody moves the proof off the machine: every entry is signed, chained and checked by an outside witness the attacker can't reach. Tampering is detected and provable, and every alert says what kind of tampering happened.

Set it up in 5 minutes View on GitHub

How it works

The agent sits next to the bank and signs every transaction into a hash chain. The witness runs on a separate server, holds only the agent's public key, and keeps checking.

Three layers

Built

Layer 2 · Heartbeat + checksum

Detects tampering and names what kind. Checks A to C below.

Next

Layer 1 · Command tripwire

Catches the intruder in the act: nano app.log is blocked and alerted, with auditd as the backstop.

Planned

Layer 3 · Break glass

Last resort: capture evidence, isolate, freeze. Unlock needs 2 of 3 key holders. Never reboots.

Layer 2 checks

A · Sealed chain

Was anything changed? Each entry is SHA-256 hashed, linked to the previous one and signed with Ed25519. The witness re-hashes everything it holds every 5 s.

B · Outside witness

Is the agent alive and honest? Signed heartbeat every 5 s, silence alert after 15 s, random hash challenges, timestamps that only move forward.

C · Truth check

Does the log match reality? The witness replays every balance and asks for real balances at random. It catches a database edit with no log entry, which a hash chain alone never sees.

What the SOC sees

Every alert carries a tamper_type, so an analyst knows what happened, not just that something did.

Setup

One laptop, no Docker, Python 3.11 or newer.

  1. Get the code and install 
    git clone https://github.com/JeevikaS-19/cybersec.git
cd cybersec
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
    git clone https://github.com/JeevikaS-19/cybersec.git
cd cybersec
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
  2. Start the witness (terminal 1) 
    python -m uvicorn --factory witness.app:create_app --port 8000
  3. Start the fake bank (terminal 2): one transfer per second into bank.db 
    python victim/bank.py
  4. Start the agent (terminal 3): reads bank.db, signs, sends to the witness 
    python agent/agent.py
  5. Check it's healthy: all three checks green, no alerts 
    curl http://127.0.0.1:8000/status
curl http://127.0.0.1:8000/alerts

Witness on a separate server

The witness belongs outside the log server. On the second machine, start it with --host 0.0.0.0 and allow port 8000 through the firewall. On the log server, point the agent at it before starting:

$env:WITNESS_URL="http://<witness-ip>:8000"
python agent/agent.py
export WITNESS_URL=http://<witness-ip>:8000
python agent/agent.py

Plug in another platform

The agent is a small sidecar. A platform plugs in by giving it transactions and balances; nothing in the platform itself changes.

  1. Map your transactions. Set BANK_DB_PATH and map your rows to the entry fields in agent/agent.py (sync_bank): txn_id, timestamp, from_account, to_account, amount_paise, and the balances after the transaction, from_balance_paise and to_balance_paise. Amounts are integer paise, never floats.
  2. Answer balance questions. For Check C, the agent reads an account's real balance from your system (bank_balance_at).
  3. Give it an identity. Set PLATFORM_ID. The agent makes its own Ed25519 key, registers the public key with the witness and keeps the private key local. It is never sent or printed.
  4. Point it at the witness. Set WITNESS_URL. Each platform gets its own independent chain, so one witness serves many platforms.

Honest limits

  • The witness learns each account's opening balance from the first entry it sees, so setup must happen on a clean system.
  • An attacker who steals the agent's key can keep signing heartbeats; Check C still catches balance changes.
  • If the network is cut, the witness sees the silence; the agent queues entries and resends them with the same seq.
